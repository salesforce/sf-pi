# SF tldraw uses deterministic Salesforce diagram profiles

Delivery: The serial P0–P4 implementation is complete. This ADR records the stable contract; the extension README and generated catalog describe the currently delivered surface.

SF tldraw will keep one `tldraw_canvas` family tool and three Salesforce-specific rendering actions: `render_salesforce_data_model`, `render_salesforce_architecture`, and `render_salesforce_sequence`. The provider-safe root tool schema remains one object; its `spec` field is an opaque object validated at execute against the three **Salesforce Diagram Spec** families (ADR 0107), and execution enforces that the selected action matches `spec.family`. The consolidated contract is `spec_version: "2.0"`, enforced directly by the three strict family schemas. Each action applies a distinct **Salesforce Diagram Profile**. The public action set is limited to `status`, `documents`, `create_document`, the three Salesforce render actions, and the lazy `cheatsheet`. Generic search, raw execution, standalone screenshots, and document-script actions are not part of the SF tldraw public interface; Pi uses the upstream `tldraw-offline` skill for generic canvas work. When the local canvas is ready, **Salesforce Diagram Routing** prefers the Salesforce render actions unless the user explicitly requests Mermaid, text, or another format; unavailable canvas state is reported before offering a fallback. This preserves a small Pi tool surface while making Salesforce output repeatable, testable, and independent of Mermaid constraints. Spec v2 rejects unknown fields at every schema level with path-specific diagnostics. Schema consolidation preserves semantic diagnostic codes and JSON paths for agent repair workflows while allowing clearer message wording. The lazy cheatsheet keeps workflow, grounding, update/readiness semantics, and one compact example per family without duplicating the field-by-field tool schema.

Every spec declares its **Diagram Grounding** as either `reference` or `org`. Every semantic element carries one or more **Diagram Evidence References**, and render artifacts expose that element-to-source mapping as inspectable provenance; SF tldraw does not claim that the renderer independently verified the cited facts. Reference-grounded workflows use official Salesforce documentation. Org-grounded workflows name an explicit authenticated org and gather schema, relationships, counts, OWD, and optional scale evidence through the existing SF Pi capability owners before rendering. Ambiguous requests ask the user to choose grounding rather than silently using an available org. Org diagrams show only a user-approved display label, org type, and observation time. **Diagram Render Privacy** rejects authentication material, Salesforce org ids, usernames or email addresses, instance URLs, and authentication URLs from every rendered field; execution-only `target_org` is neither rendered nor persisted in the artifact. Broad count enrichment uses approximate org counts by default, with exact user-visible counts opt-in. The renderer never guesses missing Salesforce facts.

Every diagram uses a compact title. Data Model canvases render no scope, grounding, source, as-of, or prose-legend text; scope and grounding metadata remain inspectable in artifacts, while a separately managed stacked **Relationships** key replaces the prose legend, sits outside the title, and shows actual black medium dotted Lookup and red medium solid Master-Detail samples when the inherited **Legend — Relationships** preference is `show` (the default). `hide` removes only the managed key in preserve mode and uses the compact title-only top margin for new, replace, and relayout renders. Data Model diagrams use pale full-card fills for Standard, Custom, and External families, org-resolved icon-tile colors, logical names, and physical API names in parentheses directly beneath the measured label bounds with an 8-unit vertical gap and no `API` prefix. Relationship-end names and field API names remain optional semantic inputs but never render on the canvas. Cardinality uses integrated vector endpoints—bar for one, crow's foot for many, and optionality circles in full mode—never tiny `1/N` text shapes. Marker anchors are computed from tldraw's clipped page-space connector terminals and local tangent, not from assumed card centers. Placement solves the marker's local anchor through tldraw's actual origin-based shape transform, and verification resolves that anchor back with `getShapePageTransform(marker).applyToPoint(...)`; hand-rolled center-rotation math is prohibited. Anchor-to-terminal distance must be at most one canvas unit for horizontal, reversed, and vertical fixtures, and placement is recomputed after render, relayout, and update. Markers sit exactly on the card boundary, visually merge with the relationship axis without an opaque decoration background, and share its direction; aligned objects use straight connectors and elbow routing is reserved for real obstacle avoidance. Relationship type is carried by the connector without a text pill: lookup is black medium dotted and master-detail is red medium solid. Official icon glyphs remain high-contrast on vivid org/SLDS color tiles instead of inheriting muted tldraw theme fills. Observation pills use solid semantic fills and fixed anchors: LDV floats over the top-right card edge and OWD floats over the bottom-center edge. Special families such as Big Objects, Platform Events, Custom Metadata, Custom Settings, and managed-package objects use badges and icons instead of additional fill colors. LDV is a configurable policy signal with a default threshold of two million records; measured skew and query risk remain optional observations. OWD is compressed into a header default plus exception pills. Record types are hidden by default and appear only when explicitly requested. Overview cards are the default; a bounded Key Fields view is optional and full field dumps are excluded. Spec v2 contains no source positions, endpoint anchors, or layout mode; every diagram uses the deterministic automatic layout. Initial graph layout adds 20–30% whitespace beyond the minimum card/connector fit so compactness never forces label or endpoint collisions.

System/Solution Architecture diagrams use neutral cards, sourced SLDS or semantic icons, one concise responsibility, ownership badges, and three connector meanings: solid directional flow, dashed asynchronous or batch flow, and thin undirected dependency. Connector labels are required, and separate directional interactions remain separate edges. External systems use neutral semantic icons. Interaction/Sequence diagrams use a dedicated static integration-flow grammar: 96-unit pastel participant headers with content-sized widths from 260–360 units; participant gaps of 140, 120, or 110 units for 1–4, 5–6, or 7–8 lanes; neutral lifelines and arrows; unboxed numbered labels on measured borderless white backings; solid request/event, dashed response, and dotted async connectors; a 118-unit message grid; and a 52-unit visual phase gap when a completed exchange changes participant pairs. Generated fallback icons are omitted from sequence headers; only explicitly declared icons render, at 44 units. Activation bars are optional, explicit, evidenced intervals and are never inferred from adjacent messages; intervals for one participant can't overlap until nested-bar routing is verified. Single-page sequence scope is limited to eight participants and 18 interactions, with warnings above six participants or 12 interactions. Self-interactions remain invalid until deterministic loop routing is verified. Sequence readiness measures participant-label containment, minimum lane separation, activation alignment, message-label bounds, row separation, connector bindings, lints, and evidence capture. Step-through behavior is excluded from the settings and tool interfaces until a complete implementation can compose Previous, Next, and Reset behavior without overwriting an existing document script; it never ships as a selectable placeholder.

The initial renderer uses Dagre for graph-family placement and fixed layout for sequence diagrams. Session startup uses only local server-config presence to publish **On-Demand Capability Availability** and performs no deferred loopback probe; explicit status, document, create, and render interactions publish verified runtime readiness. The **tldraw Runtime Floor** is v1.12, and older runtimes are incompatible rather than supported through legacy route fallbacks. Until the runtime exposes machine-readable version or capability metadata, SF tldraw establishes **tldraw Runtime Contract Proof** from the app-owned `/readme` contract and replaces that temporary proof when an upstream machine-readable endpoint becomes available. A v1.12 re-evaluation found no runtime app/API version or capability map in the per-launch server metadata or documented Canvas API object; the separate skill-install manifest is not running-process evidence, so it cannot replace the contract proof. Under **Upstream tldraw Skill Ownership**, the app remains the canonical publisher and updater of the `tldraw-offline` Pi skill; SF tldraw performs read-only **tldraw Skill Readiness** checks and provides the app's Install Agent Skills recovery path without bundling, copying, or overwriting a duplicate skill. `create_document` is a separate visible action backed by `POST /api/docs/create`; its public interface accepts only a document name, leaves placement to tldraw's default Documents directory, returns the new document id for a later render, and never runs implicitly when rendering finds no open document. The visible, non-overwriting tool call is sufficient authorization and does not add an acknowledgement field or interactive confirmation. SF tldraw never falls back to OS keystrokes or direct `.tldraw` archive generation. A new render creates a named page by default inside the selected document. Explicit update mode refreshes **Profile-Managed Diagram Elements** while preserving human placement and user-created annotations; relayout and replace are separate explicit modes. Specs that exceed the profile's readability budget require an explicit multi-page scope rather than automatic splitting or shrink-to-fit. A render is complete only at **Salesforce Diagram Readiness**: valid spec, no text overflow or overlap, and no unbound semantic connectors. Asset or evidence fallbacks remain visible warnings. Successful renders always persist the full report and full-resolution image. `summary` returns compact text, a thumbnail, and artifact references; `inline` adds bounded validation and readiness details, warnings, route metrics, and an evidence-source summary; `file_only` returns artifact references without image content.

SF tldraw will depend on a pinned `@salesforce-ux/design-system` release for all five SLDS icon categories; this package is accepted by the repository's production BSD-3-Clause license policy. Used, unchanged icons are embedded into the `.tldraw` document for portability and retain upstream license attribution. Org theme metadata is authoritative for org-grounded object icons and icon-tile color. Reference-grounded custom objects use a generic custom-object icon unless the spec declares an explicit presentation override. Product marks are excluded from the public spec until at least one official, unmodified, provenance-approved asset is bundled. An unsupported mark never appears as a selectable spec value or silently falls back under a product-mark claim.

The extension-owned Manager settings page preserves its existing visual and interaction style while its setting semantics may use shared descriptors internally. It exposes five inherited scalar preferences: Cardinality Presentation (`simplified` by default or full physical optionality), card fill (`transparent` by default or `family`), LDV threshold (`1M`, `2M`, `5M`, or `10M`; default `2M`), record-type presentation (`off` by default, with `auto` or `always` available), and **Legend — Relationships** (`show` by default or `hide`). Font, palette, icon provenance, card grammar, connector grammar, and incomplete presentation modes are not customization knobs.

The renderer must prove these profile invariants through deterministic fixture specs and visual regression evidence. A fixture is rendered in one action and asserts: zero tldraw lints; parenthesized API names with an 8-unit measured gap; cardinality-marker anchors within one unit of actual clipped connector geometry; fixed LDV/OWD pill anchors; vivid icon glyphs above their color tiles; at least the profile spacing budget; and no record-type, renderer-error, or text-cardinality artifacts by default. A fixture that violates any assertion cannot satisfy **Salesforce Diagram Readiness**.
